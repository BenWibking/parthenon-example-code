• Ownership model

− Some active elements of non-cell centered fields are shared across blocks.

− We choose a single block that owns any particular shared element. Finer blocks
take precedence, then we arbitrarily take the block with the lowest Morton
number.

− During boundary communication, unowned shared elements are overwritten with

data from owning blocks.

− During refinement the ownership model is updated to have pre-existing blocks on

a given level take precedence (B. Prather).

− Downstream codes should not have to interact directly with the ownership model.

instead of being stored in the variable itself. Flux fields have a set of default
Metadata flags. Flux fields can now easily be specified for output.

− Custom restriction operators can also be registered for flux fields for use during flux

correction.

−

Fluxes default to having the same memory layout as their parent field. For cell

are missing the outer layer of ghosts, but this gives backward compatibility and
ensures memory alignment when iterating over a cell-centered field and its fluxes.

SparsePacks

• SparsePacks provide mechanism for packing together multiple fields

over multiple blocks to access on device, very similar basic
functionality to VariablePack and MeshBlockPack.

• Why SparsePacks?

− SparsePacks support type-based packing, where every field has an
associated (empty) “name” type. This allows indexing into the pack by
overloading operator() on the name types, which works on device and
obviates the need for pulling out pack indices outside of kernels.

− Designed from the start to deal with sparse fields.
− Code is separated from MeshBlockData and MeshData.

Block-structured Forest of Octrees Meshes

• A problem domain (forest) is covered by
a set of logically hexahedral domains
(trees) that share logical faces, edges,
and nodes.

• Each tree is refined into an octree of

blocks. Location of a block in the forest
is now defined by a LogicalLocation
that includes a tree id and Morton
number.

• Logical coordinate systems of

neighboring blocks may not align, so we
require logical coordinate
transformations between trees.

Block-structured Forest of Octrees Meshes

• Allows for definition of meshes with nodes/edges of

non-standard valence.

• Even hyper-rectangular meshes are now represented
in terms of forests rather than in terms of a single
masked octree.

• Originally implemented to support the Lagrangian

hydro code Assail (A. Dempsey)

• Although Parthenon takes care of logical coordinate
transformations between blocks, Parthenon (as yet)
does not provide mechanisms for transforming
between physical coordinate systems of blocks. The
choices here are likely to downstream code
dependent.

• Forest meshes are fully compatible with non-cell

centered fields and multigrid solvers.

Block-structured Forest of Octrees Meshes

• Defining a forest mesh:

− Define a set of sptr<forest::node>s
− Hexahedral trees defined by an ordered set of their eight

corner nodes.

− Physical boundary conditions on faces defined by ordered

sets of four nodes.

− These are all combined as a

forest::ForestDefinition, which is used to construct a
forest::Forest. The Forest constructor internally
determines if it is passed a valid mesh, finds neighboring
trees, and determines logical coordinate transformations
between trees.

− Currently we only support 2D non-hyperrectangular forests.

• Forest provides methods for refining, de-refining,

block neighbor finding, and generation of unique, global
block ids in the forest.

• Under the hood, Forest and Tree rely extensively on
std::unordered_map<LogicalLocation, …>

Forest of Octrees: Communication at Trivalent Points

• Generally, boundary communication at

corners/edges of singular valence is not
straightforward.

• At a trivalent point, there are coner/edge ghost
cells on a block that do not exist on any other
tree (marked by xs). Additionally, some points
are not filled because of the ownership model.

• The fixup to the right behaves similarly to a

physical boundary condition, in that it needs to
be applied on the coarse mesh after
communication but before prolongation, then on
the fine mesh after prolongation.

Some Other New Features (part 2)

• Coalesced boundary communication

− Package all boundary-field combinations being sent from one rank to another to

minimize number of MPI messages.

− Currently implemented as two levels of buffer filling, first the regular buffers, then the

combined communication buffers. Having to support sparse fields introduces
complexity.

− Some indication that this has significant performance implications for some

downstream codes
• Metadata::Fine fields

− Creates fields with twice the resolution of other fields but that work with the

communication infrastructure.

− Currently only possess the same number of ghosts as regular fields, but this may

change.

• IndexSplit for flexible work splitting in hierarchical loops (J. Miller)
