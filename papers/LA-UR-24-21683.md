What are Parthenon and RIOT?

• Parthenon: a physics-agnostic framework to enable rapid development of

highly scalable, performance portable, multiphysics codes
− Began late 2020/early 2021
− Open source
− Supports multiple downstream applications (RIOT, Phoebus, AthenaPK, KHARMA, Artemis, Jaybenne, parthenon-hydro)
− ~36k lines of code (AMReX has ~300k lines)

• RIOT: a multiphysics code developed as an R&D activity under ASC and built

atop Parthenon
− Assess block-structured AMR relative to the cell-based AMR in xRAGE
− Enable rapid prototyping to inform production code choices, e.g. hydro in xRAGE
− Support method/algorithm R&D, e.g. higher-order methods
− Incubate shareable components like singularity-eos (github.com/lanl/singularity-eos)
− ~12k lines of code

More on task-based execution

• Task graphs are local to a rank; communication is handled by explicit calls to

non-blocking communication tasks that Parthenon provides

• Tasking code is in a single header, ~400 lines of code

− Legion is ~400k lines of code, Charm++ is ~600k lines of code

• More capability planned

− Integration with streams to support concurrent execution of kernels on GPUs (may not

require any modifications to tasking code)

− Automated, dynamic migration of kernel execution between host and device (been

waiting for architectures with a shared memory space to avoid expensive deep copies
between separate memory spaces)

Parthenon Variables

• Parthenon variables combine metadata and storage; aims to be self-

describing
• Metadata flags:

− None/Cell/Face/Edge/Node: associate a variable with a topological element
− Vector/Tensor: is it a scalar, vector, or tensor?
− Independent/Derived: is it an evolved quantity or computable?
− OneCopy: Copy pointers instead of allocating new storage
− FillGhost: Are buffers for ghost/halo exchange required?
− WithFluxes: Create storage for associated intercell fluxes
− Sparse: Will this data live everywhere or only on a subset of blocks
− Private/Provides/Requires/Overridable: Ownership
− Advected/Conserved/Intensive: Useful for downstream codes
− User defined: Apps can create arbitrary flags for their own purposes

Sparse Variables: Metadata::Sparse

• Sometimes fields are only well-

parts of a domain, e.g. density of
steel in this room

• Parthenon can leverage this to
reduce memory and walltime,
potentially dramatically

• Parthenon automatically allocates
and deallocates sparse fields as
they move through the mesh
• Through “packing,” data access
for sparse fields remains simple,
kernels can still be written

Parthenon Particles

• Parthenon also supports particles – relatively less mature compared to grid-

based variables

• Particles are held in Swarms, which are tied to mesh blocks

• Support for a variety of basic operations on particles

− Defining fields on particles, e.g. mass, energy, etc.
− Adding and removing particles
− Communicating particles between blocks and ranks
− Defrag of particle arrays

• More use cases coming online now, so likely to mature significantly in the short

term

Load balancing

• The cost to update a block can vary in space
and time for many reasons – e.g., sparse
data, local iterative solves, spatially varying
physics models

• We do not migrate tasks across resources,
e.g. Legion.  We think this is a bad idea for
our class of tightly coupled HPC applications.
Instead migrate data (blocks) as needed, up
to every cycle

•

• Automated timing to assign cost to each

block, chunk up space filling curve to try to
minimize maximum cost on a rank

Parthenon enables writing complex multiphysics codes
(while maintaining sanity)

• Parthenon design encourages composability and discourages dependency

across capabilities in downstream apps

• Design scales to many physics components while limiting complexity, reducing

demands on developers (and arguably bugs), and achieving excellent
performance and portability

• But how does one write a physics code on Parthenon?

− Driver: high-level articulation of an application, expressed through tasking
− Packages: describe the data needs (need these variables with these metadata) and

implement functionality (tasks)

RIOT is not yet physics complete for ICF

• A (probably incomplete) wish list:

− Multi-velocity to allow plasma interpenetration (likely straightforward)
− Multi-group transport/diffusion (straightforward)
− Relax ion-electron thermal equilibrium (mostly straightforward)
− Thermal conduction (Spitzer straightforward, but nonlocal may be a challenge)
− Other Non-LTE physics (depends)
− More laser-plasma interaction physics (unknown)
− Kinetic physics (unknown)
− Charged-particle transport (expensive!)
− Coarse-grained models for microscale physics, e.g. capsule grain structure (unknown)
